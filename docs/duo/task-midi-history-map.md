# 音楽史MIDI生成モデルマップ

音楽史を網羅する MIDI 生成モデルを、時代順の地図(マップ)にまとめる。地図にあるモデルを順に、
**プリセット(js/midi/presets.js)・子どもの解説(`kids`)・お手本(js/midi/demos.js)** の3点そろいで作っていく。
あわせて、地図とモデルを **LYRA の外の C++ の音楽ソフトからも呼び出せる形** にする。

## 進め方
- B(重い: Claude Codeが計画)。理由: MIDI生成の中心(`js/midi/` の engine・generators・design のスキーマ)に触れる/
  外部のアプリとの受け渡しの形(プロトコル)を新しく決める/200件を超えるモデルを何回にも分けて足す長い作業になる
- **2026-11-06、ユーザー決定: このタスクは段階0から全部の波まで、Claude Code が計画・実装・確認する(Codex に回さない)**。
  モデルの使い分け(Claude Code の提案): 段階0・生成器を足す波(tier G)・微分音の波(tier M)は Opus、プリセットだけの波(tier P)と解説は Sonnet でよい
- モデルの追加は、波(5〜10件ずつ)に分ける。各波は、計画の確認が済めば「既存の仕組みの延長」になるので、
  **生成器を足さない波は A として Codex に回せる**。生成器を足す波・微分音の仕組みが要る波は B のまま

## 設計・制約

### 1. 地図のデータ(正本)
- `models/history-map.json` に、地図の全件を置く【推測: 置き場所】。JSON にするのは、C++ からそのまま読めるようにするため
- 1件の欄:
  - `id`(英小文字と `_`。既存のプリセットと同じ id)、`era`(下の時代の区分)、`order`(地図の並び順)、`label`、`text`(1行の説明)
  - `kind`: `preset`(js/midi/presets.js)/ `beat`(ビート帳)/ `response`(応答)/ `extend`(伸ばす)
  - `tier`: 作るのに要るもの。`P` = プリセットだけ / `G` = 生成器を1つ足す / `M` = 仕組みが要る(微分音のピッチベンド・新しい拍の扱いなど)
  - `status`: `planned` / `done`。`kids`・`demo` があるか(true/false)
- **プリセット本体は今まで通り js/midi/presets.js に書く**(正本を二重にしない)。地図の JSON は「どの順に何があるか」の目録で、
  `id` でプリセット・お手本につなぐ。JSON と presets.js の食い違い(地図にあるのに無い、など)は Node の確認スクリプトで検出する

### 2. C++ から呼び出す形
- 生成の中心(`js/midi/` の theory・engine・generators・design・presets・demos)は、`document`・`AudioContext`・
  `localStorage`・IndexedDB を使っていない(2026-11-06 に grep で確認。使っているのは editor・compose・export・play だけ)。
  そこで、**設計図(JSON)+シード → 音符(JSON)/ .mid のバイト列** を返す、DOM を使わない入口を1つ作る【推測: 関数名】:
  - `LYRA.midiApi.listModels()` → 地図(JSON)
  - `LYRA.midiApi.demo(modelId)` → そのモデルのお手本の設計図
  - `LYRA.midiApi.render(design, { seed })` → `{ tempo, meter, tracks: [{ name, channel, program, notes: [{ pitch, start, duration, velocity }] }] }`
  - `LYRA.midiApi.toMidi(rendered)` → .mid のバイト列(export.js から、ファイル保存と切り離した部分を移す)
- C++ からの呼び方は3案。**おすすめは (a)**:
  - (a) **C++ 側に小さな JS 実行系(QuickJS など)を組み込み、LYRA の `js/midi/` の該当ファイルをそのまま読む**。
    生成の正本が1つのままで、LYRA を開いていなくても動く。依存が増えるのは C++ 側だけで、LYRA は素の JS のまま
  - (b) LYRA Host と同じように、開いている LYRA に、ローカルの通信で頼んで結果を受け取る。LYRA を開いている時しか使えない
  - (c) エンジンを C++ に書き直す。2つの実装を同じ結果に保ち続ける手間が大きいので、勧めない
- **Gemini が設計図を書く所(compose.js)は、入口に入れない**。外から呼ぶ時は、お手本の設計図・手で書いた設計図・
  アプリのくじで作った設計図を使う。C++ 側でも Gemini に書かせたい時は、プリセットの指示文とスキーマを JSON で出す入口を
  後から足す(キーは C++ 側で持つ。LYRA のキーを渡さない)【推測】
- 同じ設計図・同じシードなら、ブラウザーでも C++ でも同じ音符になること(決定的であること)を受け入れ条件にする

### 3. 1件のモデルを作る手順(波の中で毎回)
1. プリセット: `generators`・`pitch`・`meter`・`guide`・`style` などを書く。生成器が足りなければ(tier G)generators.js に足す
2. 子どもの解説 `kids: { title, text }`: これまでの解説はユーザーが書いた文。**新しいものは Claude Code が書く**(2026-11-06、ユーザー決定)。
   既存の解説の口調(小学生に話しかける、身近なたとえ1つ、2〜3文)に合わせる。ユーザーの文は書き換えない
3. お手本(demos.js): 手で書いた設計図と `listen`(聴きどころ)。旋律は既存曲から引用せず、ここで書く。Gemini は呼ばない
4. 地図の JSON の `status`・`kids`・`demo` を更新する
5. 確認: Node で、お手本が 10〜32 秒で音を出すこと(`docs/midi.md` の既存の確認と同じ)、プリセットの `id` が地図と一致すること
6. 耳での確認は「未確認」としてユーザーに残す
