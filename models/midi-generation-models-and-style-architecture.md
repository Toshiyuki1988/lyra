# MIDI生成モデルの類型と、様式模倣のためのアーキテクチャ指針

作曲総合アプリの設計素材として、「MIDI生成モデル」にどんな類型があり得るか、そしてバッハ〜シェーンベルクのような「〇〇風」をどう実現するかを整理する。見立て蔵の`mitategura-natural-object-midi-generation-method.md`と対を成す、モデル選定・設計指針側のドキュメント。

---

## 1. 前提となる2つのモデル

| モデル | 生成の起点 | 特徴 |
|---|---|---|
| **楽典モデル** | 調性理論・声部進行の規則 | 機能和声（トニック-ドミナント関係）、声部進行の禁則（並達五度・八度等）、非和声音の解決規則など、西洋共通practice期の理論を明示的ルールとして実装 |
| **見立て蔵モデル** | 具体的モチーフへの語彙割り当て | 入力（写真・印象等）から分解した要素ごとに、gesture_type（身振りの型）・register・occurrenceという固定語彙を割り当てて重ね合わせる。和音進行を経由せず、モチーフの具体性を身振りの層に温存する（詳細は`mitategura-natural-object-midi-generation-method.md`参照） |

この2つは軸が異なる：楽典モデルは「規則への準拠」、見立て蔵モデルは「モチーフへの語彙割り当て」。以下はこれらと別の軸に立つ追加候補。

---

## 2. その他のMIDI生成モデル候補

### 確率過程モデル（Xenakis型）
音高・リズム・密度を確率分布（ポアソン過程、ブラウン運動、マルコフ連鎖等）から直接サンプリングする。ルールでも語彙でもなく「分布のパラメータ」が設計対象。密度や粒立ちを連続的にコントロールできるため、ドローン〜密集クラスターへのなめらかな推移に向く。

### 生成文法/セルオートマトンモデル
L-systemやセルオートマトン（Wolfram型）のような単純な書き換え規則を反復適用し、自己相似的なパターンを育てる。1回の生成が「決定」ではなく「成長」になる。フラクタル的な反復・変容が欲しいアンビエント/ドローンと相性が良い。

### フェイズシフトモデル（Reich型）
同じ短い動機を複数トラックにわずかに異なるテンポ/開始位置で走らせ、位相のズレそのものを構造にする。素材は最小限のまま、時間経過だけで関係性が変わっていく。見立て蔵の「要素ごとに独立した身振り」とは対照的に、素材は1つで関係性だけを生成対象にする。

### コーパス学習モデル（n-gram/マルコフ連鎖）
雅楽や民謡など既存の旋律コーパスから遷移確率表を学習し、そのクセを保ったまま新しい旋律を生成する。楽典のような明示的規則ではなく、実例の統計的手触りを継承する。「和のクセ」を人力で規則化せずに移す手段になる。

### 制約充足モデル（OpenMusic型）
「この音域を超えない」「連続5度禁止」「この拍にはこの音階内」のような制約を先に定義し、それを満たす解をソルバーに探させる。能動的に音を生成するのではなく、条件の集合を渡して受動的に解を得る発想。

### 直接ソニフィケーションモデル
見立て蔵の「見立て」は具体物を一度AIが解釈し直してから身振りに変換するが、これは逆に外部の時系列データ（気温、潮位、株価、天体の明滅等）をほぼ無加工でMIDIパラメータに1対1マッピングする。人間の解釈を挟まない分、意外性のある動きが素材として出てくる。

### 緊張曲線モデル（出力目標駆動）
入力からではなく、先に「曲全体の緊張度/密度の時間曲線」をゴールとして定義し、それを実現するように各時点の音数・音域・和声密度を逆算して埋めていく。見立て蔵が"入力駆動"なのに対し、これは"出力目標駆動"。

### マルチエージェント対話モデル（Voyagerライク）
複数の独立エージェントが互いの直前の出力を聴いて反応するルールだけを持ち、全体は与えられずに相互作用から立ち上がる。見立て蔵が要素ごとに独立生成してマージするのに対し、こちらは要素同士が生成中に影響し合う。

### 動機変容モデル
短い動機（モチーフ）を対象化し、augmentation（拡大）/diminution（縮小）/反行/逆行/模進などの変換規則を適用して発展させる。見立て蔵のgesture_typeが「モチーフ→身振り」の1回限りの割り当てであるのに対し、こちらは「モチーフ→変換の連鎖」という時間発展のロジックを持つ。ベートーヴェン的な様式の核。

### 十二音列/セリエルモデル
固定の音列（12音を1回ずつ使い切る等）を語彙とし、原型・逆行・反行・逆行反行という決まった変換操作だけで音高を導出する。見立て蔵のgesture_typeが「モチーフ→身振り」なら、こちらは「音列→変換操作」という別の語彙体系。調性機能そのものを前提にしない点で楽典モデルと対極にある。

## 3. 作曲家様式模倣の実例分析

「バッハ風」「ストラヴィンスキー風」等は、楽典モデルへの指示（パラメータ調整）だけで実現できるか？　結論：作曲家によって答えが違う。楽典モデルに近いほど指示だけで届き、遠いほど別モデルの追加が要る。

| 作曲家 | 楽典モデルの守備範囲か | 実際に必要なもの |
|---|---|---|
| バッハ | ◎ ほぼそのまま | コラール様式の声部規則（並達五度・八度禁止、掛留音の解決、対位法の規則）は楽典モデルが最も得意とする領域そのもの。フーガの主題-応答構造だけ追加ルールが要る |
| モーツァルト | ○ | 和声語彙自体は楽典で足りるが、それだけでは「汎用的な調性音楽」にしかならない。ピリオド構造（先行4小節＋後続4小節）やアルベルティ・バスのようなフレーズ文法を別レイヤーで足す必要がある |
| ベートーヴェン | △ | 和声の骨格は楽典で可。ただしベートーヴェンらしさの核は「短い動機を執拗に変容させ続ける」動機労作で、**動機変容モデル**が別途必要 |
| ドビュッシー | × | 機能和声（トニック-ドミナント関係、非和声音の解決義務）を積極的に手放している。並行和音（プラーニング）、全音音階・教会旋法、解決しない9thの色彩的使用が核。楽典モデルとはむしろ矛盾する。見立て蔵の日本音階レイヤー（固定音高集合を機能なしで使う）の方が構造的に近い |
| ストラヴィンスキー | × | 変拍子の連続、オスティナートの並置（展開ではなくブロックの積み重ね）、八音音階、複調。和声ルールより先に拍節/リズム生成エンジンとブロック衝突配置のロジックが必要 |
| シェーンベルク | × | 無調期は調性的重力を意図的に排除、十二音技法期はさらに完全に別体系の規則（**十二音列/セリエルモデル**）に置き換わっている。楽典が前提にしている調性機能そのものを否定しているので別モデルが必須 |

**帰結**：「様式模倣」は単一モデルの選択ではなく、複数の生成軸を作曲家ごとに違う配合で組み合わせる合成である。

## 4. アーキテクチャ指針：軸分解 × プリセット合成

上記から導かれる設計方針は、「複数モデルから1つを選ぶ」構造ではなく、**作曲の要素を独立した軸に分解し、軸ごとに差し替え可能なモデル（レジストリ）を持たせ、様式はその軸の組み合わせのプリセットとして定義する**という構造。

### 想定される軸の例

| 軸 | 選べる値の例 |
|---|---|
| 音高供給軸 | 機能和声（楽典）／日本音階（見立て蔵）／八音音階／全音音階／十二音列 |
| 拍節・リズム軸 | 固定拍子／変拍子連続生成／フェイズシフト／確率過程による密度制御 |
| マクロ構造軸（展開手法） | フレーズ文法（ピリオド構造）／動機変容／オスティナートのブロック並置／持続（見立て蔵のcontinuous的発想） |
| 身振り・語彙軸 | 見立て蔵のgesture_type（10種、モチーフ単位の割り当て） |
| 現れ方軸 | 見立て蔵のoccurrence（continuous/periodic/sparse/once） |

「バッハ風」「ストラヴィンスキー風」は、各軸への具体的な値のセット＝**プリセット**として定義する。新しい様式を増やすたびにエンジンを増築するのではなく、既存の軸が揃っていればプリセットの追加だけで済む。

**具体例（ストラヴィンスキー風）**：
- 音高供給軸 → 八音音階・複調
- 拍節・リズム軸 → 変拍子連続生成
- マクロ構造軸 → オスティナートのブロック並置
- （身振り・現れ方軸は見立て蔵由来のものをそのまま流用可）

音高供給軸だけ差し替えても「ちょっと不思議な音階の曲」にしかならない——様式は複数軸の掛け合わせで生まれるため、必要な軸をすべて揃えて初めてそれらしくなる。

### 既存実装との接続

見立て蔵は既にこの構造の萌芽を持っている。`harmonic_mode`（western/japanese/hybrid）が音高供給軸、`gesture_type`が身振り語彙軸、`occurrence`が現れ方軸として、それぞれ独立変数化されレジストリ（`GESTURE_GENERATORS`等）で管理されている。

作曲総合アプリへの拡張は、以下の3ステップになる。

1. 既存の軸（音高供給・身振り語彙・現れ方）をそのまま流用する
2. 新しい軸を追加する（拍節/メーター軸、マクロ構造/展開手法軸、動機変容軸、十二音列軸など）
3. 「バッハ風」「ストラヴィンスキー風」を、各軸への値のセット＝プリセット設定として定義する（コード分岐ではなく設定データとして持つ）

この設計であれば、様式を1つ追加するコストは「新しいプリセット（設定オブジェクト）を1つ書く」ことに収束し、対応する軸のモデルが未実装の場合のみ、その軸のモデルを新規実装する、という増分的な拡張で済む。
