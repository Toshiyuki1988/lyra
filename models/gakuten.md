# 基本の楽典モデル(MIDI生成モデル `gakuten`)

LYRAが2026-09-26時点で持っているMIDI生成の方法を、1つの「MIDI生成モデル」として書き起こしたもの。
別の考え方で作る**拡張モデル**と並べて選べるようにしてあり、これはその基準になる。
「鳴らす」「MIDIにする」を押すとモデルを選ぶポップアップが出る(`chooseMidiModel()`)。第二のモデルは
見立て蔵モデル(`models/mitategura.md`)。「ビート」はモデルを選ばず、常にこのモデルの方法で作る。

- 実装: `js/midi.js`(生成・展開・書き出し)、`js/screens/ensemble.js`(入口・ソウルの知識の渡し方)
- 書き起こしの対象は「今の実装が実際にしていること」。理想や予定は書かない(書く時は「未実装」と明記する)
- 関数名は実装を探すための目印。内容はコードを読まずに理解できるように書く

---

## 1. 考え方

**音楽の骨組みは楽典(調・和声・伴奏の型・声部進行・拍節)で組む。Geminiには「記号の設計図」だけを書かせ、
設計図から実際のノートへの展開はアプリが決まった手順で行う。**

- 使っているモデルは `gemini-3.5-flash-lite`(無料枠の都合)。Liteに音番号を1音ずつ並べさせると、和声も声部の
  つながりも平凡になり、拍の数え間違いも起きやすい
- そこでGeminiには、コードネーム・伴奏の型・和音の積み方・ベースの型・ハネ・音名で書いた旋律・時間の設計図
  (起承転結など)といった、**人間の作曲家が楽譜の前に書くメモの粒度**で出させる
- 和音の転回形の選択(声部進行が近いもの)・伴奏の刻み・ベースライン・ハネ・強弱の起伏は、アプリ側で決定的に展開する
- 設計図はカードに残し(`card.midi.sketch` / `card.midi.beat`)、作り直しも設計図の単位でやり取りする
- 旋律だけはGeminiが書いた音をほぼそのまま使うので、既存曲に似せない縛りと「反芻」(2回目の点検)を掛ける

「ソウル」(美学・ジャンル・作曲家などの知識)は、**音楽の特徴 → 耳ですぐ分かる音楽の仕掛け**に翻訳させる。
音楽についての記述が無いソウル(美学の視覚的な特徴など)は、色・質感・時代・場所・感情を一般的な音楽理論で音に置き換える。

## 2. 生成の種類と入口

| 種類 | 何を出すか | 入口 | Geminiの回数 |
|---|---|---|---|
| **コード+旋律**(スケッチ) | コード進行+主旋律+ベース(+対旋律)。パートごとのトラック | 課題カードの「鳴らす」、画像カードの「鳴らす」、発言の「MIDIにする」(既定) | 2(生成+旋律の反芻)。つないだMIDIの旋律を固定する時は1 |
| **ビート** | GMドラムのリズム(10ch) | ソウルカード(美学・ジャンル・作曲家)・課題カード・画像カードの「ビート」、発言の「MIDIにする」 | 1 |
| 旋律だけ | 単旋律(音番号で直接) | 発言の「MIDIにする」 | 2(生成+反芻) |
| コード進行 | 和音(音番号で直接) | 発言の「MIDIにする」 | 1 |
| テクスチャ・ドローン | 長い音+CCオートメーション | 発言の「MIDIにする」 | 1 |
| 作り直し | 上のどれかの改善版(`_v2.mid`…) | MIDIカードの「作り直す」 | 種類と同じ |

「旋律だけ」「コード進行」「ドローン」は設計図を経ず、Geminiにノート(音番号・拍)を直接書かせる古い形。
楽典モデルの中心は**コード+旋律**と**ビート**で、以下の節はこの2つを詳しく書く。

## 3. 入力

### 3.1 アプリが集めるもの(APIを使わない)

| 入力 | 中身 |
|---|---|
| ソウルの知識 | そのソウルの全パラメータをモジュールごとにまとめた文(`LyraSoulMaterial()`)。各項目は「名前: 説明の2欄」。2欄の意味はソウルの区分で変わる(例: 美学=美学的特徴/音への翻案)。✓付きは実機で確認済み。**旋律を作る経路ではアーティスト名・曲名などの項目を外す**(`isReferenceParam()`)。プラグイン(音色)のソウルはコード+旋律には渡さない |
| つないだカード | ASTRで線がつながったまとまりのカードを1行ずつ(`cardLine()`): 気づき・課題の文、パラメータ、出典名、画像の印象、MIDIの要約など |
| 画像 | 画像カードの画像(長辺512pxのJPEG)をそのまま添付。最大3枚 |
| 固定するパート | ASTRでつないだ別のMIDIの旋律/コード/ベースを「そのまま使う」指定(3.2) |

### 3.2 生成前にユーザーへ聞くこと(ダイアログ)

| 欄 | コード+旋律 | ビート | 使われ方 |
|---|---|---|---|
| 型(時間の設計) | ○ | — | おまかせ/序破急/起承転結/AABA/ABA/一続きの物語 |
| イメージ元の光景・物語 | ○ | — | つないだ気づき・課題の文、画像の印象が初期値 |
| つないだMIDIから使うパート | ○ | — | 使わない/旋律/コード/ベース/旋律とコード(つないだMIDIごと、最大3枚) |
| 小節数 | ○(2〜32、既定8) | ○(1〜32、既定4) | |
| 取り入れたい作曲家・技法 | ○ | — | 技法だけを引用させる(5.4) |
| 参照曲・アーティスト | — | ○ | ビートの型・ノリを大いに取り入れてよい |
| ゲージ | 4本 | 3本(粒度・つんのめり・感情) | 0〜100(5.3) |
| 追加の注文 | ○ | ○ | 自由記述 |

## 4. データモデル

### 4.1 コード+旋律の設計図(`sketch`)

Geminiが1回の出力で書くJSON(`SKETCH_SCHEMA`)。キーの順は、`arc`(時間の設計図)を最初に書かせるため先頭に置いている
(構造化出力がアルファベット順に出る場合でも `arc` が先に来る。効果は未検証だが害は無い)。

```json
{
  "arc": {
    "form": "起承転結",
    "story": "時間とともに変化する光景・物語(80字以内)",
    "climaxBar": 6,
    "turn": "転で予想を裏切る仕掛け(40字以内)",
    "sections": [
      { "name": "起", "startBar": 1, "bars": 2, "scene": "霧の港", "tension": 3,
        "register": "low", "comping": "sustain", "voicing": "open", "bass": "pedal",
        "role": "提示", "ending": "半終止" }
    ]
  },
  "name": "fog_harbor.mid",
  "description": "どこがそのソウルらしいか(40字以内)",
  "concept": "コンセプト(60字以内)",
  "commentary": "解説・Cubaseで肉付けするヒント(200字以内)",
  "tempo": 72, "beatsPerBar": 4, "meters": [{ "bar": 5, "num": 7, "den": 8 }],
  "key": "D", "scale": "ドリアン", "swing": 0.3,
  "comping": "stabs", "voicing": "close", "bass": "root",
  "signature": [{ "trait": "ソウル側の特徴(15字)", "device": "それを表す音楽の仕掛け(40字)" }],
  "techniques": [{ "composer": "", "work": "", "technique": "", "use": "" }],
  "chords": [{ "symbol": "Dm9", "start": 0, "duration": 4 }, { "symbol": "C|F#", "start": 4, "duration": 4 }],
  "melody": [{ "note": "A4", "start": 0, "duration": 1.5, "velocity": 90 }],
  "counter": [],
  "markers": [{ "beat": 0, "label": "滲み:淡い" }]
}
```

| フィールド | 役割 |
|---|---|
| `arc` | 時間の設計図。セクションごとに伴奏・積み方・ベース・音域・緊張度を変える(7.6)。反芻でも「物語として聞こえるか」を点検する |
| `signature` | ソウルのどの特徴を、どんな音楽の仕掛けで表したか(3〜4個)。「そのソウルらしさ」の説明責任 |
| `techniques` | 作曲家の技法を使った時の記録(技法の名前・出典の代表作・どこで使ったか) |
| `chords` | コードネームと位置。隙間なく並べる。`|` で区切るとポリコード(最大3層、左が下)、`/` は分数コード(ベース音の指定) |
| `melody` / `counter` | 音名+オクターブ(C4=中央のド)。`start` にはハネを付けずに書かせる |
| `meters` | 途中の拍子の変化(1始まりの小節番号)。変えなければ空 |
| `markers` | 構造語彙(密度・明度・動き・空間・緊張・滲み・間・揺らぎ)で区切ったセクション名 → .mid のマーカー |

**位置の単位**: `start`・`duration`・`beat` はすべて**曲頭からの通しの4分音符の拍**(0始まり)。拍子が変わっても通しで数える
(7/8の小節は3.5拍)。小節の位置は `barList()` / `barAt()` / `meterStarts()` で計算し、`beat / beatsPerBar` で出さない。

### 4.2 語彙

| 語彙 | 値 |
|---|---|
| 伴奏の型 `comping` | `sustain`(伸ばす)/ `stabs`(短く刻む)/ `offbeat`(裏拍)/ `pulse`(8分で刻む)/ `arpeggio`(分散和音)/ `broken`(アルベルティ風)。セクションでは `none`(伴奏を抜く)も可 |
| 和音の積み方 `voicing` | `close`(密集)/ `open`(開離、drop2)/ `shell`(3度と7度)/ `cluster`(2度でぶつける)/ `quartal`(4度堆積)/ `power`(ルートと5度) |
| ベース `bass` | `root`(ルートを伸ばす)/ `root-fifth`(ルートと5度)/ `octave`(8分のオクターブ)/ `pedal`(主音を持続)/ `none` |
| 和音の高さ `register` | `low`(中心 G3)/ `mid`(既定)/ `high`(中心 A4) |
| 緊張度 `tension` | 0〜10。強弱に反映(7.6) |

### 4.3 ビートの設計図(`beat`)

```json
{
  "genre": "ブームバップ", "tempo": 90, "beatsPerBar": 4, "meters": [],
  "steps": 4, "swing": 0.4,
  "references": [{ "title": "参照したビート・曲・アーティスト", "note": "何を取り入れたか(30字)" }],
  "signature": [{ "trait": "", "device": "" }],
  "sections": [
    { "name": "メイン", "bars": 3,
      "pattern": [{ "inst": "kick", "steps": "X.....x...x....." }, { "inst": "snare", "steps": "....X.......X..o" }],
      "fill": [{ "inst": "snare", "steps": "....X...x.xXx.XX" }] }
  ]
}
```

- `steps`: 1拍の分割数(2=8分、3=3連、4=16分、6=16分3連)。`swing` は裏のステップを後ろへずらす量(3連系は0)
- `pattern` の文字列: 1文字=1ステップ。`X`=アクセント(118)、`x`=普通(96)、`o`=ゴースト(56)、`.`=休み。`|` と空白は無視
- `fill`: 区間の最後の小節だけ、書いた楽器の行を差し替える
- 楽器名 `inst`(GMドラム、27種): kick, snare, rim, clap, hat, pedalhat, openhat, crash, ride, bell, lowtom, midtom, hightom,
  floortom, tamb, cowbell, shaker, conga, congalow, bongo, bongolow, clave, woodblock, cabasa, timbale, agogo, triangle
  (別名 `bd`・`hihat`・`oh` なども受け付ける)

## 5. プロンプトの規則(Geminiに守らせること)

### 5.1 コード+旋律の考え方(`runSketch()`)

1. 手持ちの知識(と画像)から、そのソウルを最も象徴する特徴を3〜4個選ぶ。音楽の記述があれば最優先。無ければ色・質感・
   時代・場所・感情を音楽に翻訳する
2. 各特徴を、耳ですぐ分かる仕掛けにする(和声の色=maj7・9th・sus・借用和音・クロマチックメディアント・ペダル上の和音、
   旋法、リズムの感じ=ハネ・シンコペーション・ハーフタイム、テンポ、伴奏の型、旋律の輪郭=跳躍・反復・装飾)
3. 選んだ仕掛けは、コード・旋律・伴奏の型のどこかで必ず全部使う

目標は「聴いた瞬間にそのソウルらしいと分かること」。**無難で平凡な断片は失敗**と明記する。

### 5.2 音の書き方(`sketchRules()`)

- まず `arc` を書き、音はそれに従う。全区間を同じ調子で並べない
- 旋律には目的地を持たせ、`climaxBar` で最も高いか最も強い音に達する。最初の動機は形を変えて戻ってくる。
  `turn` の区間で本当に予想を裏切る。最後の区間の `ending` どおりに終える。休符で息継ぎする
- 旋律はおおむね C4〜C6、1小節あたり2〜8音。最初の1〜2小節で動機を作り、繰り返し・移高・リズムの変形で展開する。
  強拍はそのときのコードの構成音かテンション、最後はコードの構成音で終える
- 対旋律/オスティナート(`counter`)は任意。旋律とぶつからない音域に
- **自由さ**(`FREEDOM_RULES`): 途中の拍子の変化、ポリコード、クラスター、旋法の混合、非機能的な進行、オスティナート、
  ずらしたアクセントなど、無難にまとめず大胆に書いてよい

### 5.3 ゲージ(`GAUGES`、`gaugeRule()`)

ユーザーが0〜100で決め、プロンプトで「必ず守る」と指示する。Liteが守りきれない分は、アプリ側でも決まった手順で反映する。

| ゲージ | 0 | 50 | 100 | アプリ側の反映 |
|---|---|---|---|---|
| 音の粒度 `grain` | 全音符・2分音符中心、音数少 | 4分〜8分中心 | 16分・32分・3連を敷き詰める | なし(プロンプトのみ) |
| メロディの跳躍度 `leap` | 2度の順次進行だけ | 3〜5度を適度に | 6度・7度・オクターブ以上を頻繁に | なし(プロンプトのみ) |
| ダブ的なつんのめり度 `dub` | 拍どおり | 裏拍の刻みと所々の食い | 頻繁な食い・拍頭の抜き・大きな空白・こだま | `applyDub()`(7.5) |
| 感情のあるなし `emotion` | 無機質・強弱一定 | ほどよく | 山に向かって強め・溜め・大きな起伏 | `applyEmotion()`(7.5)、緊張度の効き具合 |

### 5.4 引用と独自性(`ORIGINALITY_RULE`、`techniqueRule()`)

| 対象 | 扱い |
|---|---|
| 主旋律・対旋律 | 既存曲の旋律・リフ・特徴的なフレーズ・動機を引用・模倣しない。人名・曲名が知識に出てきても似せない |
| コード進行・伴奏の型・リズムの型・音色の傾向 | ジャンル・美学に共有された語法なので、よく知られた定番進行も積極的に使ってよい |
| 作曲家の技法 | 要望があれば、その作曲家が実際に用いた技法(和声・旋法・リズム・拍子・形式・声部の扱い)を2〜4個選んで必ず使い、`techniques` に出典の代表作とともに書く。**作品の旋律・動機・特徴的なリズム音型・和声進行の並びはそのまま使わない** |
| ビート | 参照曲・アーティストのビートの型・ノリ・音数・楽器の選び方は大いに取り入れてよい。1曲のドラムパートを頭から終わりまで写し取ることはしない |
| 解説文 | 曲名・アーティスト名を出さない |

既存曲と照合する手段は無い。そのためのプロンプトの縛りと反芻(6節)である。

### 5.5 時間の設計(`narrativeRule()`)

- 型の指定があればそれに、無ければソウル・物語・カードに合う型を選ばせる
- 光景・物語の指定があれば「これを時間の流れとして音にする」。無ければ時間とともに変化する光景か物語を1つ考えさせる
- 固定するパートがあれば、その実際の音(拍・音名・長さ)を渡して「アプリが差し替えるので書き換えない」と伝え、
  テンポ・拍子をそろえさせる。旋律を固定する時は `melody` を空にし、その旋律を引き立てるコード・ベース・対旋律を書かせる

### 5.6 画像(`imageRule()`)

画像の色(色相・彩度・明暗)・光と影・質感・構図と余白・線や形の動き・奥行き・時代や場所の気配・流れている時間・感情を
読み取り、音楽に翻訳させる。ユーザーが書いた印象があれば最優先。人物の特定と、画像内の文字の引用はさせない。
印象が空の画像には、同じ出力の `impressions` に**視覚の言葉のまま**印象を書かせ、カードに残す。

### 5.7 ビート(`runBeat()`、`beatRules()`)

1. ソウル(カード・画像)に最も結びつくジャンルを1つ決める(美学など音楽以外のソウルは、結びつきの強いジャンルを選ぶ)
2. そのジャンルの定番のビート(キックとスネアの置き場所・刻み・ハネ・テンポ帯・よく使う楽器)を土台に、一聴で分かるようにする
3. ソウルらしさの仕掛けを1〜3個足して `signature` に書く(ゴーストの多さ・抜きの小節・パーカッションの色・よれ)
4. 区間(イントロ・メイン・ブレイクなど)の役割に合わせて変化をつけ、フィルで区切る

ゲージの意味はビート用に読み替える: 粒度=ハットや刻みの細かさと音数、つんのめり=キック・スネアの食い・裏の強調・拍頭の抜き、
感情=強弱の起伏。

## 6. 主旋律の反芻(`ruminateMelody()`)

主旋律を作るすべての経路(コード+旋律・旋律だけ・それらの作り直し)で、生成の後にもう1回Geminiを呼んで旋律だけを見直させる。

- 既存の有名な旋律・フックとの類似を、**音程の並び(上下の向きと幅)とリズムの両方で**点検する。最初の動機と繰り返される音型を重点的に
- 似ている(可能性がある)所は、音程の向き・跳躍の幅・リズム・休符の位置を変えて別の旋律にする。似ていなければ大きく変えない
- 保つもの: 動機の展開、休符、長さ・音域・音数、拍子の変化・ポリコード・旋法などの大胆さ、使った作曲技法、ゲージ。
  コード進行は変えさせない
- 物語の点検: 頂点へ向かうか/動機が戻ってくるか/転で裏切るか/終わり方が設計図どおりか/息継ぎがあるか/音を並べただけに聞こえないか
- 出力: 仕上げた旋律、`check`(類似と物語の点検の結論、40字)、`changes`(何を変えたか、80字)。記録はパネルに出す
- **反芻に失敗したらカードを作らない**(反芻していない旋律を出さない)
- つないだMIDIの旋律をそのまま使う時(ユーザーの旋律)は反芻しない

## 7. 設計図からノートへの展開(`renderSketch()`)

### 7.1 コードネームの解析(`parseChord()`)

- ルート(A〜G+#/b。全角・♯♭も正規化)、`/X` で分数コードのベース音
- 3和音: `m`(短3度)、`dim`(減5度)、`aug`・`+`(増5度)、`sus2`・`sus4`
- 7th: `7`(短7度)、`maj7`・`M7`・`Δ`(長7度)、`dim7`(減7度)、`ø`=`m7b5`
- 拡張: `9`・`11`・`13`(下の7thも含む)、`6`・`6/9`、`add9`、`b9`・`#11`・`b13` などの変化、`5`(パワーコード)
- ポリコード(`parseLayers()`): `|` で最大3層。1つでも読めない層があればそのコードは鳴らさない(カードに「読めなかったコードn個」)

### 7.2 和音の積み方と声部進行(`chooseVoicing()`)

1. 積み方の型ごとに、使う音と並べ方を決める(`voicingShape()`)。密集・開離は5音を超えたら完全5度、次にルートを省く
   (ルートはベースに任せる)。開離は上から2番目を1オクターブ下げる(drop2)
2. 転回形×オクターブの候補を、中心音(既定 D4、power は D3、セクションの `register` で G3/A4)の −14〜+17半音に収まる範囲で作る
3. **前の和音からの近さ**(各音から相手の最も近い音までの距離の和)と、中心からの離れ具合で最小のものを選ぶ
4. ポリコードの上の層は密集で、下の層の平均より5度〜1オクターブ半上に置く(上の層どうしも声部進行で選ぶ)

### 7.3 伴奏の型(`compOnsets()`)

小節ごとに、その小節の長さの中だけで刻む(拍子が変わっても崩れない)。

| 型 | 鳴らす位置(小節頭からの拍) | 長さ |
|---|---|---|
| sustain | コードの区間いっぱい | 区間の長さ |
| stabs | 0・1.5・3 | 0.4 |
| offbeat | 各拍の裏(0.5, 1.5…) | 0.4 |
| pulse | 8分ごと | 0.42 |
| arpeggio | 8分ごと。和音の音を上って下りる順 | 0.5 |
| broken | 8分ごと。下・上・中・上の順(アルベルティ風) | 0.5 |
| none | 鳴らさない | — |

コードが変わる瞬間は必ず鳴らす(裏拍の型だけは、鳴らす所が1つも無い時に限る)。強さは小節頭76・それ以外66(分散和音は78・68)、sustainは62。旋律は書かれた強さ(無ければ92)。

### 7.4 ベース

- 音域は G#1〜G2(C2+ピッチクラス、G2を超えたら1オクターブ下げる)。`pedal` はキーの主音
- `root`: コードの頭と各小節の頭で鳴らし、次の音まで伸ばす
- `root-fifth`: それに加えて小節の真ん中(奇数拍子は切り上げ)で5度(高すぎれば4度下)
- `octave`: 8分ごとにオクターブを交互に(長さ0.45)
- 強さは小節頭88・それ以外80

### 7.5 旋律の整えと、ゲージ・ハネの反映

- 旋律・対旋律: 音名→音番号、C3〜C7に折り返し、位置と長さを1/12拍(16分と3連の両方が乗る格子)に丸める、最大256音
- **ハネ**: 8分の裏(拍の .5)を `swing/6` 拍後ろへ(swing=1で3連の3つ目)。長さも合わせる
- **つんのめり**(`applyDub()`、コード・ベースだけ):
  - 30以上: 小節頭のコード・ベースを16分早く食う(65未満は1小節おき)
  - 50以上: 伸ばさない伴奏の刻みの後に、付点8分後のこだま(強さ45%)。80以上は2回目(1.5拍後、22%)。次の刻みまで間が無ければ付けない
- **感情**(`applyEmotion()`、全パート): パートごとに強弱の平均を保ったまま、幅を 0→平ら、50→そのまま、100→2倍にする

### 7.6 時間の設計図の反映

- セクションは `startBar` の小節の頭から始まり、コードの頭の拍でどのセクションかを決める
- セクションごとに伴奏の型・積み方・ベース・和音の高さを切り替える(指定が無ければトップレベルの既定値)
- 緊張度で強弱を動かす: `強さ × (1 + (緊張度−5) × 0.05 × 感情ゲージ/50)`。感情0なら動かさない

### 7.7 仕上げ

- 同じパート・同じ高さの音が重なったら、前の音を後の音の頭で切る(`trimOverlaps()`)
- ノートは最大1500。パートは `melody` / `chords` / `bass` / `counter`

### 7.8 ビートの展開(`renderBeat()`)

- 区間ごと・小節ごとに、各楽器の文字列を1ステップ=1/steps拍で読む。区間の最後の小節は `fill` の行で差し替え
- 1小節より短い行は、1拍の倍数の長さなら繰り返し、それ以外(「X」だけのクラッシュなど)は残りを休みにする
- ハネ: 偶数分割の裏のステップを `swing × ステップ長 / 3` 後ろへ
- ヒューマナイズ(感情ゲージ): 小節頭以外の発音を最大±0.012×感情 拍揺らし、強さを ±(2+12×感情) 揺らす。その後 `applyEmotion()`
- 音の長さ: オープンハット0.45、クラッシュ1、ライド0.5、ライドベル0.4、トライアングル0.5、ほかはステップ長の9割(最大0.2)
- 区間の頭にマーカー。最大32小節

## 8. つないだMIDIのパートの差し替え(`applyFixedParts()`)

- ASTRでつないだMIDI(改善の系譜の外のもの)の旋律/コード/ベースを、ダイアログで選ぶとそのまま使う
- テンポ・拍子・ハネを、最初の固定元のMIDIにそろえてから展開する(`alignToSource()`)
- 生成後、そのパートの音を固定元の音で置き換える。パートの無いMIDIは全部の音をそのパートとして使う
- 同じパートを2枚から取ろうとしたら先のカードを優先。差し替えの記録は `midi.fixedFrom`

---

## 9. 作り直し(`reviseMidi()`)

- 渡すもの: 前回の設計図(旋律は音名に戻す)、これまでのコメント(古い順に最大4つ)、今回のコメント、
  ASTRでそのMIDIにつないだカードとソウルの知識、手で編集していれば実際の音(設計図より優先して尊重させる)
- コメントで触れていない部分はなるべく前回を保つ。コメントが空でも、技法の要望かつないだものがあれば実行できる
- 改善版は右隣に置き、元のカードと自動で線を結ぶ(`_v2.mid`, `_v3.mid`…)。つないだソウルを `memberIds` に引き継ぐ

## 10. 出力

### 10.1 カードのデータ

```
card.midi = {
  tempo, beatsPerBar, meters: [{bar, num, den}],
  notes: [{ part, pitch, start, duration, velocity }],   // 拍単位
  cc: [{ controller, label, points: [{beat, value}] }],  // ドローンなど
  markers: [{ beat, label }], tempoChanges: [{ beat, bpm }],
  sketch? | beat?,   // 設計図(作り直し・パネル・編集画面が使う)
  gauges?, kind?, rumination?, fixedFrom?, edited?
}
card.concept / card.commentary / card.description   // コンセプト・解説・一言
```

### 10.2 .mid(SMF format 1、PPQ 480)

- 1トラック目(コンダクター): 曲名、拍子(変わる所ごと)、テンポ、テンポ変化、マーカー
- 書き出し方(`buildSmf(card, mode)`):
  - 「1トラックで」(既定のおすすめ): 全パートを1トラック・ch1に(ドラムだけのMIDIはch10)
  - 「パート別」: 旋律・コード・ベース・対旋律を別トラック(ch1〜)、ドラムはch10(GMの約束)
  - パート1つずつ
- CCは最初の音のトラックに入れる
- 範囲を選んでいれば、その範囲だけを切り出す(範囲の頭を0拍目に、またぐ音は範囲の中だけ)

## 11. 既知の限界

- 旋律の既存曲との類似は、プロンプトの縛りと反芻だけで防いでいる(照合手段は無い)
- 粒度・跳躍のゲージはプロンプトだけで、Liteが守りきれないことがある
- Liteが通しの拍を正しく数えられるか(拍子の変化の多い時)は実機で十分には確かめていない
- 和声の組み立ては西洋の機能和声・ジャズの語彙(コードネーム)が土台。コード進行を経ない音楽(音響的な身振り・
  日本音階の旋律線だけの音楽など)は表しにくい → 拡張モデルで補う想定
- 音色は扱わない(.midには音色の指定を入れない。試聴の音色はアプリの試聴用)
